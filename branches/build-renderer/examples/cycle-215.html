context

Context — the architectural cost the outage exposed

Today's setup fuses three concerns on one VPS:

Concern Today Cost
Build atom-on-VPS runs docker compose build via studio-blue-green-deploy Action VPS down = no deploy possible
Orchestrate atom-core (ovh-ts) manages containers via Komodo VPS down = atom UI down
Run Same VPS serves production traffic VPS down = site down

When the VPS went offline 2026-05-12 (~3h before this session, reason: OVH billing), the result was: no live site, no atom UI, no deploy path for committed code. The cycle 211 Phase 2 mega-menu work landed in git (1941aca4) but couldn't ship.

The session worked around it via local pnpm build && pnpm start — proving the iteration loop can be local without infrastructure changes. But the deploy path remained blocked end-to-end.

Core observation: build is what's most expensive AND most VPS-specific in the current setup. Decouple build from the same host that serves traffic, and the VPS becomes interchangeable. Adding orchestration redundancy (multi-Server atom) is a smaller next step. Adding host redundancy is the final step.

outtake

Out-take

The outage was useful diagnostically: it surfaced that the "blue-green deploy" pattern (cycle 162) protects against deploy-failure but not against host-failure. The next architectural layer is host-redundancy, and the gating step is decoupling build from host. Phase 1 does that. Phase 2 + 3 compound the benefit but neither requires Phase 1 to be done first — they're independent levers.

The simplest mental model: today's atom is "monolith deploying its own host." Where this cycle lands: "atom orchestrates N hosts where images come from somewhere else." The day Curtis says "let's just put this on a second cheap VPS for fun," all three phases pay off simultaneously.

No work to do now. Revisit when OVH is back + Curtis has budget for the Phase 1.b piece — the single biggest leverage and the right entry point.

parity-discipline

Dev/prod parity discipline — gating prerequisite for Phase 2+

Curtis surfaced 2026-05-12 the risk: once local atom feels legitimate (Phase 2), an agent might silently work against a partial mirror and not notice it diverges from prod. Three structural fixes that need to land BEFORE Phase 2 carries real work:

  1. Compose files are canonical in Gravicity/infra — local atom Server doesn't fork them. Differences expressed as env overrides, never as separate compose files.

  2. Agent self-awareness — an env probe at boot (hostname + docker context show + tailscale ip cross-check) declares which world the agent is in. Result lands in preload/status.

  3. Service-graph body doc — one doc that says "studio depends on soma-hub for auth, soma-arzadon for media, postgres for X, all on gravicity-network." Without that graph, an agent can't tell when it's running against a partial mirror.

Filed as Phase 0 prerequisite.
